# 系统开发与运行说明

## 1. 文档目的

本文档用于说明安全事件智能处置后端项目的开发结构、运行方式、主流程状态流转和模块接入位置。

当前第一版以“给出主链运行方式、团队知道代码往哪里接”为目标。真实平台能力、完整数据库设计、最终接口规范等内容后续按实际资料补齐。

## 2. 当前范围

### 2.1 已确定

- 开发语言：Python。
- 数据库选型：MySQL。
- 后端框架：FastAPI。
- 数据模型：统一 `EventContext`。
- 主流程：提供固定样例输入和主流程调用入口。
- 状态推进：由编排层统一控制，业务模块不直接改状态。
- 平台接入：通过适配层隔离，当前实现固定样例，真实 XDR/MCP 待接。

### 2.2 当前占位

- XDR OpenAPI 路径、鉴权方式和返回字段映射。
- MCP 工具输入输出。
- FastGPT/OpenClaw 调用方式。
- 真实处置动作权限和审批策略。
- MySQL 生产级表拆分、索引和迁移策略。
- 前端最终接口路径。

## 4. 环境要求

### 4.1 Python

要求 Python 3.11+。

本地开发建议使用：

```bash
/opt/homebrew/bin/python3.11
```

### 4.2 依赖

项目依赖在 `pyproject.toml` 中维护，核心依赖包括：

- `fastapi`：HTTP API。
- `pydantic`：请求、响应和领域模型。
- `uvicorn`：本地开发服务。
- `sqlalchemy`：MySQL 数据访问。
- `pymysql`：MySQL Python 驱动。

安装方式：

```bash
python3.11 -m venv .venv
source .venv/bin/activate
pip install -e .
cp .env.example .env
```

### 4.3 MySQL

数据库选型已确定为 MySQL。

当前默认仍使用内存存储，是为了在数据库连接信息未完全确定前减少本地运行依赖。切换 MySQL 只需要改环境变量。

本地 MySQL：

```bash
docker compose up -d mysql
```

环境变量：

```bash
# 修改 .env：
STORAGE_BACKEND=mysql
MYSQL_HOST=127.0.0.1
MYSQL_PORT=3306
MYSQL_USER=sec_agent
MYSQL_PASSWORD=sec_agent
MYSQL_DATABASE=sec_agent
MYSQL_AUTO_CREATE_SCHEMA=true
```

## 6. 运行方式

### 6.1 启动 HTTP 服务

```bash
uvicorn sec_agent.main:app --reload
```

默认地址：

```text
http://127.0.0.1:8000
```

健康检查：

```bash
curl http://127.0.0.1:8000/health
```

检查返回 JSON 中的 `status` 字段是否为 `ok`，并确认 `storage_backend`、`platform_backend` 与当前 `.env` 配置一致。

### 6.2 通过脚本运行主流程

```bash
PYTHONPATH=src python3.11 -m sec_agent.scripts.run_flow
```

该脚本会启动固定样例流程，并在流程进入审批状态时提交一次本地演示审批。运行时重点观察输出中的 `event_id`、最终 `status` 和状态时间线。

## 7. HTTP 接口

当前接口是 MVP 最小接口，最终路径命名后续可调整。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/health` | 健康检查 |
| `POST` | `/runs` | 启动一次事件处理 |
| `GET` | `/events` | 查询事件列表 |
| `GET` | `/events/{event_id}` | 查询事件详情 |
| `GET` | `/events/{event_id}/timeline` | 查询状态时间线 |
| `POST` | `/events/{event_id}/approval` | 提交审批结果 |
| `GET` | `/metrics` | 查询基础指标 |

### 7.1 启动固定样例

```bash
curl -X POST http://127.0.0.1:8000/runs \
  -H 'content-type: application/json' \
  -d '{"source":"fixed_sample","sample_id":"webshell-001"}'
```

从响应中复制 `event_id`。固定样例属于高风险处置演示场景，通常会进入等待审批状态，下一步使用该 `event_id` 调用审批接口。

### 7.2 审批通过

```bash
curl -X POST http://127.0.0.1:8000/events/{event_id}/approval \
  -H 'content-type: application/json' \
  -d '{"approved":true,"approver":"demo-user","reason":"演示审批","idempotency_key":"approval-demo-001"}'
```

审批接口返回完整 `EventContext`，重点查看 `status`、`response.execution`、`response.verification` 和 `timeline` 字段。

## 8. 主流程说明

最小主流程：

```text
固定样例告警
  ↓
告警接入
  ↓
告警关联
  ↓
风险研判
  ↓
深度调查 Agent
  ↓
处置决策
  ↓
人工审批
  ↓
有状态 Mock 执行
  ↓
独立验证
  ↓
完成
```

状态流转：

```text
RECEIVED
  ↓
CORRELATING
  ↓
TRIAGED
  ↓
INVESTIGATING
  ↓
DECISION_READY
  ↓
APPROVAL_REQUIRED
  ↓
EXECUTING
  ↓
VERIFYING
  ↓
COMPLETED
```

异常或未满足条件时可能进入：

- `HUMAN_REQUIRED`：需要人工接管。
- `FAILED`：流程无法继续。

## 9. 模块说明与接入位置

### 9.1 API 层

位置：`src/sec_agent/api/`

职责：

- 暴露 HTTP 接口。
- 处理请求参数。
- 调用编排服务。
- 返回统一上下文或列表摘要。

后续前端联调主要改：

- `src/sec_agent/api/routes/events.py`
- `src/sec_agent/api/routes/metrics.py`

### 9.2 Bootstrap 层

位置：`src/sec_agent/bootstrap/container.py`

职责：

- 读取配置。
- 创建平台适配器。
- 创建 repository。
- 创建主流程编排器。

后续增加真实平台适配器或替换数据库实现时，优先改这里。

### 9.3 Domain 层

位置：`src/sec_agent/domain/`

职责：

- 定义 `EventContext`。
- 定义告警、事件、研判、调查、处置、验证等核心对象。
- 定义业务状态和状态机。

约束：

- 状态只能由编排层推进。
- 业务模块只返回本阶段结果，不直接覆盖上游结果。
- 原始证据只保存引用，不在上下文里重复保存大体积原文。

### 9.4 Services 层

位置：`src/sec_agent/services/`

模块接入位置：

| 文件 | 模块 | 当前状态 |
| --- | --- | --- |
| `ingest.py` | 告警接入 | 固定样例可用，XDR 占位 |
| `correlation.py` | 告警关联 | 最小关联逻辑可用 |
| `triage.py` | 风险研判 | 简单规则基线可用 |
| `investigation.py` | 深度调查 Agent | 固定工具调用可用 |
| `response.py` | 处置决策、执行、验证 | 有状态 Mock 可用 |
| `orchestrator.py` | 状态编排 | 统一推进主流程状态 |

后续开发原则：

- 优先在对应 service 内补业务逻辑。
- 不要把平台调用散落在业务模块里，平台能力统一走 `platforms/`。
- 不要绕过 `orchestrator.py` 修改状态。

### 9.5 Platforms 层

位置：`src/sec_agent/platforms/`

职责：

- 屏蔽 XDR OpenAPI、MCP、固定样例等不同来源。
- 对上层提供统一能力：
  - 查询告警或事件。
  - 查询日志和证据。
  - 查询资产和漏洞。
  - 调用安全分析能力。
  - 发起受控处置。
  - 查询动作状态。

实现位置：

- `base.py`：平台适配器协议。
- `fixed_sample.py`：固定样例实现。

真实 XDR 接入时建议新增：

```text
src/sec_agent/platforms/xdr_openapi.py
```

### 9.6 Repositories 层

位置：`src/sec_agent/repositories/`

职责：

- 持久化 `EventContext`。
- 管理审批和工具执行幂等键。

实现位置：

- `memory.py`：本地演示和测试使用。
- `mysql.py`：MySQL 实现。

### 9.7 Infrastructure 层

位置：`src/sec_agent/infrastructure/mysql/`

职责：

- 定义 MySQL 表模型。
- 创建 SQLAlchemy engine/session。
- 执行最小 schema 创建。

最小表：

| 表 | 说明 |
| --- | --- |
| `security_events` | 保存完整事件上下文 JSON，并冗余常用查询字段 |
| `idempotency_keys` | 保存审批和工具调用幂等键 |

## 10. 数据结构说明

### 10.1 EventContext

统一上下文位于：[src/sec_agent/domain/models.py](../../src/sec_agent/domain/models.py)

核心字段：

| 字段 | 说明 |
| --- | --- |
| `schema_version` | 上下文结构版本 |
| `trace_id` | 一次完整处理链路追踪编号 |
| `run_id` | 本次运行编号 |
| `event_id` | 安全事件编号 |
| `status` | 当前业务状态 |
| `source` | 数据来源 |
| `alert_refs` | 原始告警引用 |
| `event_summary` | 关联后的安全事件摘要 |
| `triage` | 风险研判结果 |
| `investigation` | 深度调查结果 |
| `response` | 处置、执行和验证结果 |
| `timeline` | 状态变化和关键操作 |
| `errors` | 异常、降级和人工接管信息 |

### 10.2 ToolRequest 和 ToolResult

工具请求和工具结果位于：[src/sec_agent/domain/models.py](../../src/sec_agent/domain/models.py)

`ToolRequest` 用于描述一次工具调用请求，核心字段：

| 字段 | 说明 |
| --- | --- |
| `call_id` | 单次工具调用编号 |
| `trace_id` | 完整处理链路追踪编号 |
| `event_id` | 所属安全事件编号 |
| `stage` | 发起工具调用时所处业务阶段 |
| `tool_name` | 工具名称，如 `evidence_lookup` |
| `action_name` | 工具动作名称，如 `query_related_evidence` |
| `params` | 工具参数，禁止放入明文凭据 |
| `param_refs` | 大体积参数或外部数据引用 |
| `reason` | 调用原因，用于审计和前端展示 |
| `dry_run` | 是否试运行 |
| `idempotency_key` | 幂等编号 |
| `risk_level` | 工具风险等级 |
| `approval_status` | 审批状态 |
| `approval_id` | 审批记录引用 |
| `timeout_seconds` | 调用超时时间 |
| `attempt` / `max_attempts` | 当前重试次数和最大重试次数 |
| `sensitive_param_keys` | 需要审计脱敏的参数键 |

`ToolResult` 用于描述一次工具调用结果，核心字段：

| 字段 | 说明 |
| --- | --- |
| `call_id` | 对应请求的调用编号 |
| `trace_id` | 完整处理链路追踪编号 |
| `event_id` | 所属安全事件编号 |
| `tool_name` / `action_name` | 对应工具和动作 |
| `idempotency_key` | 对应请求幂等编号 |
| `status` | 成功、失败或部分成功 |
| `summary` | 结果摘要 |
| `raw_result_ref` | 原始结果引用 |
| `evidence_refs` | 产生或命中的证据引用 |
| `output_refs` | 工具输出引用 |
| `output_preview` | 可直接展示的轻量结果摘要 |
| `retryable` | 是否允许重试 |
| `error_type` / `error_message` | 结构化错误类型和错误说明 |
| `platform_status` | 底层平台状态 |
| `external_side_effect` | 是否产生外部副作用 |
| `side_effect_type` | 无副作用、只读、状态变更 |
| `started_at` / `ended_at` / `duration_ms` | 调用耗时信息 |

接入真实工具时，业务模块只创建 `ToolRequest`，具体调用放在 `platforms/` 适配层中完成；返回结果必须转换成 `ToolResult`，不要把平台原始响应直接透传给上层业务。

## 12. 提交规则

完整 Git 新手操作说明见：[仓库提交规则.md](仓库提交规则.md)

### 12.1 提交前检查

提交前至少执行：

```bash
PYTHONPATH=src python3.11 -m unittest discover -s tests
PYTHONPATH=src python3.11 -m sec_agent.scripts.run_flow
```

如果修改了 HTTP 接口，还需要启动服务并检查：

```bash
uvicorn sec_agent.main:app --reload
curl http://127.0.0.1:8000/health
```

### 12.2 提交内容要求

- 每次提交尽量聚焦一个模块或一个明确任务。
- 代码、测试、文档保持同步；改主流程必须同步改测试和运行说明。
- 不提交 `.venv`、`__pycache__`、本地日志、临时文件、IDE 私有配置。
- 不提交明文密码、Token、连接码、真实平台凭据。
- 新增配置项要同步补充 `.env.example` 和本文档配置说明。
- 新增外部依赖要写入 `pyproject.toml`，并说明用途。
- 新增接口要写清楚请求、响应、状态变化和异常情况。

### 12.3 模块接入规则

- API 只做请求响应和参数转换，不写核心业务逻辑。
- 业务逻辑优先放在 `services/` 对应模块中。
- 状态推进只能通过 `services/orchestrator.py` 和 `domain/state_machine.py` 完成。
- 平台调用统一走 `platforms/`，不要散落在业务 service 中。
- 数据持久化统一走 `repositories/`，不要在业务 service 里直接写 SQL。
- MySQL 表结构暂放在 `infrastructure/mysql/`，后续如引入迁移工具再调整。

### 12.4 安全规则

- 凭据不进源码、日志、前端响应和文档。
- 高风险真实处置动作必须保留审批流程。
- 工具调用必须带 `trace_id` 和 `idempotency_key`。
- 执行动作后必须有独立验证结果。
- 无法确认平台返回或证据不足时，进入 `HUMAN_REQUIRED`，不要编造结果。
