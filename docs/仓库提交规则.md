# 仓库提交规则

## 1. 文档目的

本文档目标是让大家可以安全地拉取代码、创建分支、提交代码、推送代码、处理冲突和做基础回滚。

第一原则：不要直接在主分支上开发。每个任务都新建自己的功能分支，完成后再合并。

## 2. 常用概念

| 名词 | 含义 |
| --- | --- |
| 仓库 | 保存项目代码的地方 |
| 本地仓库 | 自己电脑上的代码目录 |
| 远程仓库 | GitHub、GitLab、Gitee 等平台上的代码仓库 |
| 分支 | 一条独立开发线 |
| 主分支 | 稳定代码分支，通常叫 `main` 或 `master` |
| 功能分支 | 每个人为一个任务创建的开发分支 |
| 提交 | 把本地修改保存为一次版本记录 |
| 推送 | 把本地提交上传到远程仓库 |
| 拉取 | 从远程仓库下载最新代码 |
| 合并 | 把一个分支的代码合到另一个分支 |
| 冲突 | 两个人改了同一处代码，Git 无法自动判断保留谁 |
| 回滚 | 撤销某次错误修改 |

## 3. 基本要求

### 3.1 分支要求

- `main`：主分支，只保留可运行代码。
- `dev`：开发集成分支，如果团队暂时没有 `dev`，可以先只用 `main`。
- `feature/xxx`：功能分支，用于开发新功能。
- `fix/xxx`：修复分支，用于修 bug。
- `docs/xxx`：文档分支，用于改文档。

推荐分支命名：

```text
feature/xdr-alert-ingest
feature/triage-rule
fix/state-transition-error
docs/git-guide
```

不推荐：

```text
mycode
test
aaa
new
```

### 3.2 提交要求

每次提交尽量只做一件事。

提交前必须确认主流程还能跑：

```bash
PYTHONPATH=src python3.11 -m unittest discover -s tests
PYTHONPATH=src python3.11 -m sec_agent.scripts.run_flow
```

如果只修改文档，可以不跑主流程，但要确认 Markdown 内容能正常打开。

### 3.3 禁止提交

不要提交这些内容：

```text
.venv/
__pycache__/
*.pyc
.DS_Store
本地日志
临时文件
真实密码
Token
连接码
平台密钥
```

如果不确定某个文件能不能提交，先问负责仓库的同学。

## 4. 首次使用 Git

### 4.1 设置用户名和邮箱

只需要设置一次：

```bash
git config --global user.name "你的名字"
git config --global user.email "你的邮箱"
```

查看是否设置成功：

```bash
git config --global --list
```

### 4.2 克隆仓库

进入你想放项目的目录：

```bash
cd ~/code
```

克隆仓库：

```bash
git clone 仓库地址
```

进入项目：

```bash
cd spark-sec-agent-be
```

查看当前分支：

```bash
git branch
```

查看当前状态：

```bash
git status
```

## 5. 每天开始开发前

每天写代码前，先拉最新代码。

### 5.1 切到主分支

如果团队使用 `main`：

```bash
git switch main
```

如果团队使用 `dev`：

```bash
git switch dev
```

### 5.2 拉取最新代码

```bash
git pull
```

如果看到 `Already up to date.`，说明本地已经是最新。

## 6. 新建分支开发

不要直接在 `main` 或 `dev` 上改代码。

### 6.1 新建并切换到功能分支

```bash
git switch -c feature/你的任务名
```

例子：

```bash
git switch -c feature/triage-rule
```

### 6.2 确认当前分支

```bash
git branch
```

带 `*` 的就是当前分支，例如：

```text
  main
* feature/triage-rule
```

## 7. 查看修改内容

### 7.1 查看哪些文件变了

```bash
git status
```

### 7.2 查看具体改了什么

```bash
git diff
```

如果只想看某个文件：

```bash
git diff 文件路径
```

例子：

```bash
git diff src/sec_agent/services/triage.py
```

## 8. 提交代码

### 8.1 添加要提交的文件

添加单个文件：

```bash
git add 文件路径
```

例子：

```bash
git add src/sec_agent/services/triage.py
```

添加多个文件：

```bash
git add 文件1 文件2
```

添加当前目录下所有修改：

```bash
git add .
```

新手建议优先使用单个文件添加，避免把不该提交的文件加进去。

### 8.2 提交

```bash
git commit -m "提交说明"
```

好的提交说明：

```bash
git commit -m "feat: add triage baseline rule"
git commit -m "fix: handle approval rejected state"
git commit -m "docs: add git contribution guide"
```

不好的提交说明：

```bash
git commit -m "update"
git commit -m "修改"
git commit -m "111"
```

### 8.3 提交说明格式

推荐格式：

```text
类型: 简短说明
```

常用类型：

| 类型 | 说明 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 修复问题 |
| `docs` | 文档 |
| `test` | 测试 |
| `refactor` | 重构 |
| `chore` | 构建、配置、杂项 |

例子：

```text
feat: add fixed sample platform adapter
fix: reject invalid status transition
docs: add run flow result
test: cover approval rejected path
```

## 9. 推送代码

第一次推送新分支：

```bash
git push -u origin 当前分支名
```

例子：

```bash
git push -u origin feature/triage-rule
```

之后继续推送同一个分支：

```bash
git push
```

推送成功后，在远程仓库页面创建合并请求：

- GitHub 叫 Pull Request，简称 PR。
- GitLab/Gitee 叫 Merge Request，简称 MR。

## 10. 合并代码

推荐流程：

1. 本地完成开发。
2. 本地测试通过。
3. 推送功能分支。
4. 在平台上创建 PR/MR。
5. 找同学 Review。
6. Review 通过后合并到 `dev` 或 `main`。

不要在没有 Review 的情况下直接合并主分支，除非团队明确允许。

## 11. 开发过程中同步主分支代码

如果你开发时间较长，别人可能已经合并了新代码。建议每天同步一次主分支。

假设你的分支是 `feature/triage-rule`，主分支是 `main`。

### 11.1 保存当前修改

先看状态：

```bash
git status
```

如果有未提交修改，建议先提交：

```bash
git add .
git commit -m "chore: save current work"
```

### 11.2 拉取主分支最新代码

```bash
git switch main
git pull
```

### 11.3 回到自己的分支

```bash
git switch feature/triage-rule
```

### 11.4 合并主分支到自己的分支

```bash
git merge main
```

如果没有冲突，Git 会自动合并。

如果有冲突，按下一章处理。

## 12. 冲突解决

### 12.1 什么是冲突

当两个人改了同一个文件的同一段内容，Git 不知道保留哪一份，就会产生冲突。

冲突文件里会出现类似内容：

```text
<<<<<<< HEAD
这是你当前分支的内容
=======
这是别人分支合进来的内容
>>>>>>> main
```

### 12.2 解决冲突步骤

1. 查看冲突文件：

```bash
git status
```

2. 打开冲突文件，找到：

```text
<<<<<<<
=======
>>>>>>>
```

3. 手动改成最终想保留的内容。

4. 删除冲突标记。

5. 重新添加文件：

```bash
git add 冲突文件路径
```

6. 完成合并提交：

```bash
git commit
```

如果 Git 自动打开编辑器，不会编辑的话，可以退出后用：

```bash
git commit -m "merge: resolve conflict with main"
```

### 12.3 冲突解决原则

- 不确定保留谁时，不要猜，找对应模块负责人确认。
- 不要直接删掉别人的代码。
- 解决冲突后必须跑测试。
- 如果冲突发生在主流程状态机、数据库模型、接口返回字段，必须找相关同学一起确认。

### 12.4 放弃本次合并

如果冲突太乱，不想继续本次合并：

```bash
git merge --abort
```

这会回到合并前的状态。

## 13. 拉取代码遇到冲突

执行：

```bash
git pull
```

如果提示有本地修改无法合并，先看状态：

```bash
git status
```

### 13.1 本地修改还要保留

先提交本地修改：

```bash
git add .
git commit -m "chore: save local changes"
git pull
```

### 13.2 本地修改不要了

危险操作，执行前确认这些修改真的不要：

```bash
git restore 文件路径
git pull
```

如果有多个文件都不要了：

```bash
git restore .
git pull
```

不要随便执行 `git reset --hard`。这会直接丢弃本地修改，新手不建议使用。

## 14. 回滚操作

回滚前先确认你想撤销的是哪一种情况。

### 14.1 文件改错了，还没提交

查看状态：

```bash
git status
```

撤销某个文件：

```bash
git restore 文件路径
```

撤销所有未提交修改：

```bash
git restore .
```

注意：执行后未提交内容会丢失。

### 14.2 已经 `git add`，但还没提交

取消添加：

```bash
git restore --staged 文件路径
```

然后如果还想撤销文件修改：

```bash
git restore 文件路径
```

### 14.3 已经提交，但还没推送

如果只是提交说明写错：

```bash
git commit --amend -m "新的提交说明"
```

如果想撤销最后一次提交，但保留文件修改：

```bash
git reset --soft HEAD~1
```

如果想撤销最后一次提交，并且不要这些修改：

```bash
git reset --hard HEAD~1
```

注意：`git reset --hard` 会丢代码，新手执行前必须确认。

### 14.4 已经推送到远程

不要直接改历史。推荐用 `revert` 新增一次反向提交：

```bash
git revert 提交ID
```

提交 ID 可以通过下面命令查看：

```bash
git log --oneline
```

`revert` 会生成一个新提交，用于撤销指定提交的影响。它比强制推送安全。

## 15. 常见问题

### 15.1 忘记当前在哪个分支

```bash
git branch
```

带 `*` 的就是当前分支。

### 15.2 不知道本地有没有修改

```bash
git status
```

### 15.3 提交时发现加错文件

还没提交时：

```bash
git restore --staged 文件路径
```

已经提交但没推送时：

```bash
git reset --soft HEAD~1
```

然后重新 `git add` 正确文件并提交。

### 15.4 推送失败，提示远程有新提交

先拉取远程代码：

```bash
git pull
```

如果有冲突，按“冲突解决”章节处理。

处理完成后再推送：

```bash
git push
```

### 15.5 切换分支失败，提示有未提交修改

先看状态：

```bash
git status
```

如果修改要保留：

```bash
git add .
git commit -m "chore: save work before switch branch"
```

如果修改不要：

```bash
git restore .
```

然后再切换分支。

## 16. 本项目提交前检查清单

提交前逐项确认：

- [ ] 当前不在 `main` 或 `dev` 上直接开发。
- [ ] 分支名能看出任务含义。
- [ ] `git status` 中没有不该提交的文件。
- [ ] 没有提交 `.venv`、`__pycache__`、日志、临时文件。
- [ ] 没有提交密码、Token、连接码、真实平台凭据。
- [ ] 代码能通过测试。
- [ ] 主流程能跑通，或说明为什么本次不需要跑。
- [ ] 修改接口、状态、模块接入方式时，同步更新文档。
- [ ] 提交说明清楚说明本次做了什么。

本项目推荐提交前执行：

```bash
PYTHONPATH=src python3.11 -m unittest discover -s tests
PYTHONPATH=src python3.11 -m sec_agent.scripts.run_flow
```

## 17. 推荐工作流

完整流程：

```bash
# 1. 切到主分支并更新
git switch main
git pull

# 2. 新建自己的功能分支
git switch -c feature/your-task

# 3. 开发代码

# 4. 查看修改
git status
git diff

# 5. 运行测试
PYTHONPATH=src python3.11 -m unittest discover -s tests
PYTHONPATH=src python3.11 -m sec_agent.scripts.run_flow

# 6. 添加并提交
git add 需要提交的文件
git commit -m "feat: your change"

# 7. 推送远程分支
git push -u origin feature/your-task

# 8. 在远程仓库页面创建 PR/MR
```

## 18. 遇到不确定情况怎么办

如果遇到下面情况，不要硬操作：

- 不知道冲突文件该保留谁。
- 想执行 `git reset --hard`。
- 想强制推送。
- 不确定某个文件是否包含敏感信息。
- 不确定是否应该直接合并主分支。
- 回滚已经推送到远程的提交。

处理方式：

1. 先执行：

```bash
git status
```

2. 可以把输出截图或复制给仓库Owner。

3. 等待确认后再操作。
